# After `wasi_p2_*`: a separate WASI host library (plan, not started)

**Status (2026-10-23): both are moved.** `natify-sh/fusedwasi`, branch `wasi-p2`, has WASI 0.2 (`fusedwasi/p2/`, C and Python, with the tests, the audits and the comparison with Wasmtime) and WASI 0.1 (`fusedwasi/p1/`: `wasi_p1_core.h`, `wasi_p1_files_win32.h`, `wasi_p1.h`, `wasi_p1_unstable.h`, C only). Every C name has the prefix of the library (`fusedwasi_p1_*`, `FUSEDWASI_P1_*`, `fusedwasi_p2_*`, ...), and 0.1 no longer includes `wasm-rt.h`: it reads the memory through the pointer to its base and the one to its size (`fusedwasi_p1_bind`, called by the glue with `&memory->data, &memory->size`). wasmext depends on `fusedwasi` (the owner chose a dependency over a submodule: the Python package carries the headers, `fusedwasi.get_include()`); until fusedwasi is released the source is the branch (`[tool.uv.sources]`; `pip install wasmext` needs the release first). What stays in wasmext is `wasi_python.h` (the host of 0.1 that is Python: `wasmext_wasi_new` and the file backend through `os`), the glue, and the tests that need `wasm2c`. The file backend that a host gives is selected with `FUSEDWASI_P1_HOST_FS` (it was `FUSEDWASI_P1_HOST_FS`). The ABI fingerprint was renewed for the move. (The text below is the plan as it was written.) The owner leans to **option B** below: "something like uvwasi, but with WASI 0.2 and later WASI 0.3, that works with a *fused component model → core wasm* module". The decision is taken when `wasi_p2_*` is finished (`http`, the Windows parts of `filesystem` and `sockets`, a test against Wasmtime). The numbers in the first table are from a reading of the code on 2026-10-23 (line counts checked); the days are an estimate, not a measurement.

## What there is

| Layer | Files | Lines | Depends on |
|---|---|---|---|
| WASI 0.1 core | `c/wasi_core.h`, `wasi_preview1.h`, `wasi_unstable.h` | 2 370 + 2 × ~37 | `wasm-rt.h`, but only through `wasm_rt_memory_t *memory` (`->data` 39 times, `->size` once) |

| WASI 0.2 | `c/p2/wasi_p2_{core,clocks,random,io,cli,filesystem,sockets,http}.h` | ~5 300 | libc and POSIX (Windows only for the core, clocks, random, io, cli) |

`p2/` is already a library in all but name: header-only, `static inline`, no global and no thread-local, one `wasi_p2_state` with hooks (`trap`, `realloc` = `cabi_realloc`, `wait`, `exit`, `random_bytes`, clocks, `socket_addr_check`, `http_check`, `http_send`), a memory is `{base, size}` for each component (what a fused module with several memories needs), and `c/p2/` is not read by the fingerprint of the ABI. 0.1 comes apart almost mechanically: `wasm_rt_memory_t` becomes `{data, size}`, `FUSEDWASI_P1_HOST_FS` and the 12 `wasi_be_*` functions become the place of an outside back end.

## The options

* **A, 0.2 only.** A repository (or a directory with its own README, licence, tests and CI) with `p2/`. About 3–5 days: skeleton, SPDX headers, a C test runner (the expected results are now in `tests/test_wasi_p2_*.py` and must move), CI on Linux/macOS/Windows, and wasmext takes it back as a vendored copy or a submodule (the headers are copied to `build/wasmext/<module>/` already).
* **B, 0.1 + 0.2, and 0.3 later (the choice leaned to).** A: plus 4–7 days for 0.1: no `wasm_rt`, a neutral prefix instead of `wasmext_wasi_*`, the Windows files. 0.1 and 0.2 stay **two independent groups of headers in one repository**: they have different errno maps and different file back ends, and sharing code would cost much and give little. The main risk is the fingerprint of the ABI: `tests/test_abi.py` hashes every file in `src/wasmext/c/`, so taking 0.1 out changes it; whether that is "a change of the ABI" is for [abi_policy.md](abi_policy.md) to say (not studied yet).
* **C, nothing is separated.** The headers stay in wasmext. Cheapest; the library is not usable without it.

## What B needs besides moving files

1. **The glue to a fused module.** wasm2c names an import `w2c_<module>_<name>(host, ...)` and a fused module has one memory for each component, so a call of the library `(state, comp, ...)` needs a one-line wrapper for each import (up to 138 for the command world, 63 more for http), with `comp` taken from the suffix of the name. Generate it from a table of names and signatures (the WIT is the source: `docs/experiments/wasi_p2_audit/` already computes the flat signatures); keep the generator in the library or in wasmext's `_gen.py` (open).
2. **WASI 0.3.** The big change is async: `stream<T>`, `future<T>` and `async` functions replace the `pollable`/`wait` loop of 0.2 (a task that waits has to be able to give up the thread). The state of the host must therefore not assume that one call is one run to the end; keep that in mind in `wasi_p2_state` (the `wait` hook is where a scheduler would come in). Nothing of 0.3 is designed yet.
3. **Fused modules are the input.** The library does not read components; the fusing (components → one core module with the lowered imports) is done before it, and the library is only the host side of the imports that remain (`wasi:*`). The tests of the library should therefore include a fused module, not only C drivers that call the functions directly.
4. **Security as a public duty.** The confinement of paths and the policy of sockets and http become promises to other people: fuzzing, a policy for reports, and the tests of the WASI testsuite for 0.1 and a comparison with Wasmtime for 0.2.
5. **Versions.** A public library means semantic versions; while it is alpha it can say that it is unstable.

## What it does to the check of the ABI (the owner, 2026-10-23)

The fingerprint of the ABI reads every file directly in `src/wasmext/c/`, and the WASI of 0.1 is there (`wasi_core.h`, the back ends), so each fix inside WASI renewed the fingerprint without touching the ABI (it happened three times on 2026-10-23: the escape by a slash, the comparison with uvwasi, `fd_allocate` on macOS). With WASI in `fusedwasi` the fingerprint covers what is the ABI (the record, the capsule, the glue), and a change of WASI is a version of `fusedwasi`, which wasmext pins. The border that stays to be kept is the one between the two: the slot of an import `(fn, user)` and the state that is passed (`wasi_p2_state`, the state of 0.1) are the contract, so a change of their shape is a change of the major version of `fusedwasi` and of the ABI of wasmext both. `c/p2/` is out of the fingerprint already; the 0.1 part must first lose its `wasm_rt_memory_t` (see the table above) to be able to leave.

What follows is the submodule version, kept for the record: So: the submodule's commit pins the version of the WASI that a wasmext has; the build and `pyproject` must find the headers in the submodule (sdist/wheel have to carry them); the fingerprint of the ABI reads `src/wasmext/c/` only, which no longer has WASI; CI checks out with `submodules: true`.
* **wasmhost (the owner, 2026-10-23): later `wasmhost` has to run fused wasm modules with the pure (Python) version of `fusedwasi`.** So `fusedwasi` has two sides with one behaviour: the C headers (for wasm2c: wasmext and the executables) and the pure Python package (for the engines that `wasmhost` fronts: a memory and values in, values out). That is the twin that `c/p2/` and `p2/` already are, and it fixes two things: the Python side must depend on nothing of wasmext (no `wasmext` import, only a memory object and the arguments of the flat ABI), and the parity tests (the same scenario in C and in Python) move with the code and stay in the library. The glue that binds the imports of a fused module to the host functions is then written once per side.
